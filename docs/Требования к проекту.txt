Общая информация
В качестве практической части курса вам нужно будет оформить одну задачу машинного обучения в репозиторий индустриального уровня со всеми необходимыми компонентами (они будут описаны в заданиях ниже). Смысл курса состоит в том, чтобы вы были способны самостоятельно произвести все необходимые операции, использовать современные эффективные инструменты и получить конечный результат в виде стабильно работающего сервиса, а не только цифры и графики в jupyter notebook-е. Проект нужно выбирать так, чтобы в нём вы смогли применить все ключевые компоненты, изучаемые в программе.


В течение семестра вам нужно будет выбрать задачу, описать её в предложенном формате, создать репозиторий и работать над ним постепенно, выполняя выданные задания неделя за неделей с помощью коммитов в основную ветку этого репозитория.
Ссылку на репозиторий вы передадите однажды, а далее по ней мы будем проверять наличие сделанных заданий в указанные даты.
Дедлайны и баллы
Задания с критериями и баллами будут публиковаться в этом документе по мере того, как мы с вами будем проходить темы в курсе.


Проверка работ также будет происходить поэтапно и публиковаться в канале курса.
Для сдачи работ будет два дедлайна:
* Мягкий: примерно неделя от момента выдачи
* Жёсткий: примерно неделя от мягкого
До мягкого дедлайна вы получите полные баллы. После мягкого дедлайна, но до жёсткого будет применён понижающий коэффициент 0.7 на заработанные вами баллы. После жёсткого коэффициент будет понижен до 0.5 и такие работы будут проверены к экзамену.
Для еженедельных тестов отсечки баллов 0.6 и 0.3 соответственно.


Крайний срок сдачи работ - за две недели до даты экзамена. Работы, присланные позже, будут учитываться только на пересдаче. Это, в частности, означает, что если в семестре ничего не делать, а прийти только на экзамен (даже со сделанной работой), то можно получить только баллы за экзамен и по итогу сдачи отправиться на пересдачу. Иными словами проект является обязательным и его необходимо делать в течение семестра.


Во второй части курса будет проведено peer review ваших проектов, об этом объявим отдельно. Экспертная оценка (ручная) будет проведена после полной реализации пайплайна обучения и peer review и будет являться финальной точкой проверки.


Экзамен будет проходить устно с опорой на проект (будут задаваться вопросы по нему, почему делали так, а не иначе, какие могут быть варианты), по формату это обычный устный экзамен, программу опубликуем ближе к концу когда пройдём большую часть.
На экзамене нужно знать все темы, покрытые в курсе, не только то, что вы использовали в своём проекте.


Тесты по теории будут проходить в гугл формах, там необходимо будет ответить на несложные вопросы по материалам занятий. Один тест занимает около 15 минут. Чтобы подготовиться к нему, полезно повторить соответствующее занятие. Это является стимулом чтобы смотреть лекции вовремя (а не в последний день перед экзаменом). Результаты этих тестов будут учтены в финальной оценке (см ниже).
В конце вас ждёт финальный тест, там будут вопросы по всем занятиям, он займёт примерно 2 часа. Это можно считать аналогом письменного экзамена.


Для получения любой положительной оценки необходимым являются выполнение проекта не менее чем на 50% первичных баллов (до применения коэффициента по сроку), а также сдача устного экзамена на удовлетворительно и выше.


Составные части оценки:

Task 2: Training code
Необходимо создать открытый репозиторий на github, в нём создать пакет на Python, который будет являться валидным с точки зрения пакетирования и решать вашу задачу (из предыдущей части).


В репозитории должны быть реализованы (детали ниже в разделах):
* загрузка данных
* препроцессинг данных (если необходимо)
* тренировка


Как мы будем проверять вашу работу (обобщённые шаги):
1. клонируем репозиторий
2. создаём новый чистый virtualenv (по инструкции)
3. устанавливаем зависимости (по инструкции)
4. `pre-commit install` - ожидаем успешную установку
5. `pre-commit run -a` - ожидаем успешный результат
6. запускаем тренировку - также ожидаем успех и снижение лосса

Code quality tools (10 баллов) *
Необходимо использовать pre-commit c базовыми хуками pre-commit, black, isort, flake8, prettier (для не Python файлов). Связку black, isort, flake8 можно заменить на ruff (рекомендуется).
Все хуки должны быть соответствующе настроены в pyproject.toml или другом файле в зависимости от инструмента (не стоит использовать захардкоженные в вызов параметры).
Также необходимо, чтобы запуск pre-commit run -a не выдавал ошибок (зелёные результаты).
Training framework (15 баллов) *
Базовой опцией является PyTorch Lightning, также вы можете воспользоваться другими фреймворками, которые мы обсуждали, но в них как правило меньше возможностей. Hugging face не рекомендуется, нужно обсуждать лично.
Обучение должно быть сделано с помощью выбранного фреймворка, используя доступные в нём возможности (не нужно строить велосипеды).
Не пишите весь код единым полотном - делите на функции, вызывайте их. В файле для тренировки не должна быть описана вся логика: препроцессинг, подгрузка данных и тд.
Data management (10 баллов) *
Необходимо использовать dvc для хранения данных.
В качестве хранилища можно использовать гугл диск, яндекс диск, либо s3 (убедитесь, что оно доступно), либо локальное хранилище.


Скачивание данных с помощью dvc необходимо встроить в имеющиеся команды train и infer, для этого у dvc есть python api (на крайний случай можно использовать CLI из Python кода).


В итоговой версии репозитория должна быть директория .dvc с файлом config, в которым вы должны прописать хранилища. Для данных и моделей укажите два разных хранилища.


Если вы используете локальное хранилище, необходимо написать функцию download_data(), которая скачивает ваши данные из открытых источников.
Hydra (10 баллов) *
Переведите основные гиперпараметры препроцессинга, обучения и постпроцессинга в yaml конфиги hydra. Сами конфиги лучше всего расположить в папке configs в корне репозитория.
Конфиги должны быть сгруппированы по тем операциям, которые вы проводите (например свой файл для препроцессинга, другой для основной модели, третий для сервигна и т.д.). Используйте иерархические конфиги. Другими словами - нужна единая точка входа в конфиги c defaults (ориентируйтесь на то, как было показано на семинаре).


В коде не должно быть магических констант. Их можно вынести либо в отдельный Python файл (если они глобальные и их не предполагается менять), либо под управление hydra.
Logging (10 баллов) *
Необходимо добавить логирование ваших основных метрик и функций потерь (всего не менее 3 графиков). Также в эксперимент записывать использованные гиперпараметры и версию кода (git commit id). Считайте, что сервер mlflow уже поднят по адресу 127.0.0.1:8080 (вы можете поднимать его локально для тестов по этому же адресу). Адрес добавьте в поле конфига.


Можно использовать дополнительные системы логирования (например wandb), если вам это нужно.
После обучения положите в папку plots графики обучения вашей модели: например, лосс / метрика(и) на тренировке/валидации.

* Не использовать warnings.filterwarnings("ignore"). Никогда не делайте этого в продакшен любых проектах. Это огромный задел на отстреливание себе ноги. Разработчики пакетов пишут предостережения чтобы сделать вашу жизнь проще - лучше всего выполните их советы.

   * Используйте dvc или аналоги
* Название репозитория (в т.ч. url) должно отражать смысл вашего проекта (e.g. cats-vs-dogs), а не название курса (e.g. mlops_homework).
   * Использовать - [dash] в качестве разделителя (не _ [underscore])
* Нужно назвать питон пакет (aka папка с вашим кодом) по правилам питона (snake_case), а не любым другим способом (e.g. MYopsTools)
* Также питон пакет (aka папку с кодом) необходимо называть согласно смыслу вашего проекта, не src или my_project
* Используйте дефолтный .gitignore для Питона (а не пустой), его дополняйте необходимыми вам путями. Дефолтный конфиг гуглится и даже предлагается вам гитхабом при создании репозитория.
* Файлы с кодом должны называться в snake_case, не в CamelCase (e.g. Dataset.py)
* Не использовать argparse, вместо него fire, click, hydra или другой инструмент для cli.
* Не использовать однобуквенные переменные кроме i, j, k. Вместо этого давайте переменным семантически наполненные имена (data или features вместо X и т.д.)
* Не оставлять закомменченный код (сами комментарии оставлять можно, но не мусорные участки кода)
* Не указывать в названии проекта название курса и в целом mlops
* Импорты должны быть в начале файлов
* Не хранить в корне сами скрипты (помимо тех, что запускают инференс - эти можно)
